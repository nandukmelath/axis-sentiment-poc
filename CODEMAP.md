## Root — config, database, orchestrators

**Purpose.** The repo-root control plane: one config module that defines the entire brand/source/LLM universe, one dual-dialect data-access module every other package writes through, four alternative pipeline runners (legacy, windowed, max-harvest, continuous), a terminal SQL console, an MCP server that exposes the whole stack as AI-drivable tools, a SQLite-to-Postgres migration script, and a static HTML picture of the DAG. Nothing here does sentiment work itself — it wires, schedules, stores, and exposes the work done in fetch/, transform/, analyze/, warehouse/, and analytics/.

**Data flow.** config.py loads .env and hands every module the brand aliases, 20 source configs, LLM provider chain, and FETCH_LIMITS. A runner (run_window for the dashboard RUN button, run_harvest for the GitHub Actions cron every 12h) calls fetch.run_fetch.run() -> db.upsert_posts() into raw_posts; then transform.beam_transform -> clean_posts; then analyze.run_analyze.run_baseline() (VADER, free, scores everything) and run_llm() (LLM depth only on the db.get_needs_llm() queue: model='vader-fast' AND sentiment<>'positive') -> analysis. db.create_view() joins those two into the scored_posts view that the dashboard, FastAPI, and MCP all read. run_harvest then arms the ADR-001 DQ gate (warehouse.build.ensure_tables() + db.snapshot_tables() over 19 GATED_TABLES), rebuilds clusters -> star schema -> 13 marts, runs warehouse.dq_checks, and either db.drop_snapshots() (publish) or db.restore_tables() (roll back to last-good and sys.exit(1)). db.py's DATABASE_URL switch is what lets the identical code run on local axis.db for the demo and Neon Postgres in the cloud.


### `db.py` · ~349 lines  **[DEMO]**

The data-access layer. One SQLAlchemy engine built from DATABASE_URL (defaults to sqlite:///axis.db), DIALECT detection, SQLite PRAGMAs (busy_timeout=30000, synchronous=NORMAL, and a written explanation of why NOT WAL - the file is shared across NTFS/WSL-9p), and Postgres pool tuning for a Supabase/Neon pooler (pool_recycle=1800, pool_size=5, pool_pre_ping). DDL creates 4 tables: raw_posts (PK source_id, engagement/reply_count/retweet_count/quote_count/view_count/bookmark_count/conversation_id/raw_json), analysis (PK source_id, 27 cols: sentiment, score, emotion, sarcasm, intent, urgency, urgency_reason, product, root_cause, rbi_category, recommended_team, recommended_action, churn_risk, fraud_signal, fraud_type, pii_present, aspects_json, cluster_id, model, text_masked, pii_types), clusters, and clean_posts (Beam output: text_hash, is_duplicate, spam_flag). Plus 6 indexes, an additive-only MIGRATIONS dict applied by migrate(), and create_view() building the scored_posts view (raw_posts LEFT JOIN analysis) that the dashboard/API/MCP all read. Write path: dialect-aware _upsert() (INSERT OR REPLACE/IGNORE vs ON CONFLICT DO UPDATE/NOTHING) behind upsert_posts / upsert_analysis / upsert_cluster / upsert_rows / insert_rows, plus replace_rows() which does DELETE+INSERT in ONE transaction so a live reader never sees an empty table. Queue helpers get_unanalyzed / get_untransformed / get_needs_llm. parse_dt() uses format='mixed' with a comment documenting the bug it fixed (pandas inferring one format NULLed ~87% of created_date). Bottom third is the ADR-001 DQ gate: GATED_TABLES (19 derived tables), snapshot_tables() -> {t}__bak, restore_tables(), drop_snapshots().

**Why it exists.** Every package writes through this file; it is the only thing that knows the schema. The DATABASE_URL switch is the whole 'runs on your laptop, runs on cloud Postgres, same code' claim. The snapshot/restore functions are the mechanism behind 'bad data never reaches the dashboard'. Without it there is no schema, no idempotent upsert, and no rollback.

### `run_harvest.py` · ~166 lines  **[DEMO]**

The production runner - what GitHub Actions (.github/workflows/pipeline.yml, cron '0 */12 * * *') executes. 14 numbered stages wrapped in _step(), which times each stage and captures any exception into summary[name+'_error'] so one failure never aborts the harvest. Order: init_db -> config.validate() warnings -> _counts() BEFORE -> fetch.run_fetch.run(window=None) -> transform.beam_transform.run() -> analyze.run_analyze.run_baseline() -> run_llm(limit=None) -> warehouse.build.ensure_tables() + db.snapshot_tables() (arms the DQ gate) -> analyze.embed_cluster.main() -> warehouse.build.main('all') -> warehouse.resolution.build_interactions() -> analytics.features.build_all() + intelligence.build_all() -> analytics.translate.translate(limit=200) -> analytics.competitor.run(limit=40) -> actions.build_alerts/weekly_digest/draft_replies(limit=25) -> analyze.exec_summary.main() -> analytics.ops.run_all() -> warehouse.dq_checks.run(). On any failed check it calls db.restore_tables() and prints 'DQ FAILED ... restored last-good'; on pass it calls db.drop_snapshots() and prints 'published'. __main__ does sys.exit(1) on gate failure so the cron goes red.

**Why it exists.** This is the file that turns a pile of scripts into a governed pipeline: fetch-all -> classify-all -> build-all -> validate -> publish-or-roll-back. It is the honest answer to 'what runs in production and what happens when it produces garbage'.

### `mcp_server.py` · ~468 lines  **[DEMO]**

A FastMCP server named 'axis-sentiment' exposing the whole stack over MCP stdio (registered in .mcp.json). 9 query tools: system_status (row counts for raw_posts/analysis/clusters/clean_posts/fact_mention, date span, which provider keys are set, DB URL with the password regex-masked), describe_schema, search_mentions (filters over the scored_posts view: query/source/sentiment/urgency/team/since/fraud_only/churn_only), get_kpis, get_issues (adds the emerging flag: recent_share>=0.6 AND avg_score<0 AND size>=2), priority_queue (priority = urgency_weight x (1+sqrt(engagement)) x (0.5+negativity)), get_mart (reads any mart_/fact_/dim_/vw_ table), run_sql, get_exec_brief. 7 action tools that shell out via _run(): fetch_sources, classify, rebuild_clusters, generate_exec_brief, build_warehouse, run_pipeline (calls run_window), backfill_x. 4 MCP resources: axis://status, axis://schema, axis://exec-brief, axis://kpis. Safety: AXIS_MCP_READONLY=1 makes _guard_action() block every mutating tool; run_sql rejects multi-statement input, anything not starting with SELECT/WITH, and a _FORBIDDEN regex of write/DDL keywords; MAX_ROWS=500; AXIS_MCP_TIMEOUT default 300s.

**Why it exists.** The 'you can talk to your bank's social data' moment - an assistant can ask for the priority queue or emerging issues without anyone opening the dashboard. The readonly flag and SQL guard are the pre-baked answer to the security question a bank will ask.

### `run_window.py` · ~71 lines  **[DEMO]**

Backs the dashboard's RUN button (dashboard/app.py:108 spawns `python -m run_window --window ...`). run(window) executes 5 independently try/except-wrapped stages: print config.validate() warnings; fetch.run_fetch.run(window=window); transform.beam_transform.run(); db.init_db() + analyze.run_analyze.run_baseline(); warehouse.build.main('all'); then analytics features.build_all/intelligence.build_all/actions.build_alerts/actions.weekly_digest/ops.run_all. Emits a single machine-parseable line `RUN_WINDOW {json}` with per-stage results or `<stage>_error` strings. argparse accepts --window 1h|1d|1m. Deliberately runs no LLM step - keyless and fast.

**Why it exists.** Makes the demo interactive rather than a static screenshot: the client picks 'last 1 hour', the pipeline actually runs, the war-room refreshes. Stage isolation means one dead scraper degrades the run instead of blanking the dashboard mid-presentation.

### `config.py` · ~217 lines

Module-level constants only, plus one function. Loads .env from the repo root. Defines DB_PATH; LLM knobs (GEMINI_MODEL, EMBED_MODEL, BATCH_SIZE=12, SLEEP_BETWEEN_BATCHES=4.5 tuned to ~13rpm under the free 15rpm cap, MAX_RETRIES=5); CLUSTER_DISTANCE=0.35; BRAND/BRAND_ALIASES/COMPETITORS (HDFC, ICICI, SBI, Kotak); the source universe - 12 SUBREDDITS, PLAY_APP_ID='com.axis.mobile', NEWS_QUERIES, TWITTER_MODE (default 'csv'), MASTODON_TAGS, X_HANDLES (4 handles verified live), X_BACKFILL_* windowing, ScrapeBadger targets for LinkedIn/TikTok/ConsumerComplaints/MouthShut/Trustpilot/Google Maps, RSS_NEWS_FEEDS (5 outlets, with notes on which feeds were excluded and why), GDELT_QUERIES; the cascade thresholds CASCADE and VADER_POS=0.6; the pluggable LLM layer - LLM_PROVIDER, LLM_FALLBACKS chain, BRIEF_MODEL, and an OPENAI_COMPAT dict mapping 7 providers (freellmapi/groq/openai/openrouter/deepseek/together/cerebras) to (base_url, key_env, default_model), plus Ollama for keyless local; FETCH_LIMITS scaled by the FETCH_MULT env var; and the governance block - AXIS_HANDLES (for detecting a bank reply in a thread), SLA_RESPONSE_HOURS=24, PII_MASK=1, BEAM_RUNNER. validate() returns a list of human-readable warnings (never raises) about missing keys, and live-probes the freellmapi endpoint.

**Why it exists.** Single source of truth. Re-pointing this system at a different bank is edits to BRAND/BRAND_ALIASES/COMPETITORS/handles/app-ids in this one file - that is the commercial argument. validate() is why the runners print 'running on keyless sources only' instead of silently producing an empty dashboard.

### `query.py` · ~90 lines  **[DEMO]**

Terminal SQL console over the same db module (so it follows DATABASE_URL). 8 named PRESETS: sources, sentiment, urgency, issues (clusters by size), fraud (joins raw_posts to analysis WHERE fraud_signal=1), urgent (urgency IN critical/high with owning team), recent, models (row count per classifier model). main() dispatches: no args -> overview with table row counts; 'tables'; 'schema <table>'; a preset name; `-i` for an interactive sql> REPL; or any raw SQL string passed through. Reconfigures stdout to UTF-8 to avoid Windows cp1252 crashes.

**Why it exists.** The credibility tool. When a client says 'show me the actual fraud-flagged posts, not a chart', `python query.py fraud` puts raw rows on screen in one command. Also the fastest way to answer an unanticipated question live.

### `live_ingest.py` · ~34 lines

A 34-line continuous loop. Module-level argparse (--interval 120, --analyze-limit 12, --no-analyze), then `while True:` spawning subprocesses `-m fetch.run_fetch`, then (unless --no-analyze) `-m analyze.run_analyze --limit N` and `-m analyze.embed_cluster`, printing a timestamp per cycle and sleeping --interval seconds.

**Why it exists.** The 'it's genuinely live' prop - run it in a second terminal and new mentions appear in the auto-refreshing dashboard without anyone touching a button. Without it the dashboard only changes when RUN is pressed.

### `run_all.py` · ~17 lines

17 lines. A STEPS list of 4 subprocess invocations - fetch.run_fetch, analyze.run_analyze --limit 60, analyze.embed_cluster, analyze.exec_summary - run in sequence with check=False. No transform stage, no warehouse, no marts, no DQ gate.

**Why it exists.** The original v1 orchestrator from before the warehouse and mart layers existed. Superseded by run_window (interactive) and run_harvest (production), but still the command README.md:57 and the dashboard's empty-state message (dashboard/app.py:163) tell a user to run.

### `migrate_to_pg.py` · ~41 lines

One-shot SQLite-to-Postgres copy. Asserts 'postgres' is in DATABASE_URL, imports db (which binds to the target), calls db.init_db() to create tables + the scored_posts view on Postgres, opens a second engine against the local axis.db, then pandas-reads raw_posts / analysis / clusters and writes them with to_sql(if_exists='append'). Its own docstring says 'Idempotent-ish: uses append, so run it once (or TRUNCATE the target tables before re-running).'

**Why it exists.** The 'we can lift this onto Supabase/Neon' story; RUNBOOK.md:84 and AIRFLOW.md:13 both point users here. Note it is not the current tool - tools/migrate_pg.py supersedes it (see gotchas).

## fetch/ — data ingestion (9 live sources)

**Purpose.** The ingestion tier: ~20 independent source adapters that each pull public Axis Bank mentions from a different channel (news RSS, app stores, Reddit, X, forums, review sites, social scrapes), normalize them into one flat dict shape, and land them into the single `raw_posts` table keyed by `source_id`. It exists so the rest of the pipeline (clean/transform → VADER+LLM classification → star schema → 13 marts → Streamlit/FastAPI) only ever has to understand ONE row shape, and so that any one dead/blocked/rate-limited source degrades to an empty list instead of killing the harvest.

**Data flow.** `run_fetch.run()` calls `init_db()`, then walks the `SOURCES` list of `(name, fn)` pairs, calling each adapter's zero-arg `fetch()` inside its own try/except so one failure only prints `[name] FAILED`. Every adapter returns a list of dicts with the same keys — `source_id, source, author, text, url, created_at, engagement, lang` plus optional `author_name, reply_count, retweet_count, quote_count, view_count, bookmark_count, conversation_id, raw_json`. run_fetch dedups the merged list into a `{source_id: row}` map (last source in SOURCES order wins on collision), drops rows with no `text`, optionally filters by an ISO time window via `_within()` / `cutoff()` (`1h`/`1d`/`1m`), then calls `db.upsert_posts(rows)` which stamps `fetched_at` and does an `INSERT OR IGNORE` on `raw_posts` PK `source_id`. Downstream, `db.get_untransformed()` and `db.get_unanalyzed()` LEFT-JOIN `raw_posts` against `clean_posts` / `analysis` to pick up whatever is new. Three plumbing layers sit under the adapters: `webutil.py` (browser UA + https-only GET + `brand_match` regex) for keyless HTTP sources, `scrapebadger.py` (paid X advanced-search API, 429 backoff, `CreditsExhausted` on HTTP 402) and `scrapebadger_web.py` (`web_scrape`/`sb_get`/`extract_items` wrappers over ScrapeBadger's universal `/v1/web/scrape` + native endpoints) for the eight paid scrape-based sources.

## analyze/ — the AI layer (VADER + LLM)

**Purpose.** This is the "brain" of the POC: it turns each raw social post into a decision-grade structured record (sentiment, emotion, sarcasm, per-aspect opinion, intent, urgency, RBI grievance category, owning team, recommended action, churn/fraud flags, PII flags, theme, summary, confidence) and writes it to the `analysis` table that every downstream mart, dashboard panel, and API endpoint reads. It exists because raw text is unactionable — the bank needs a routable ticket, not a tweet. It uses a two-tier cascade (free VADER baseline for everything, LLM depth only on non-positive posts) to keep cost near zero, masks PII with an offline regex+Luhn layer before any text leaves the box, and dispatches LLM calls through a multi-provider failover chain so no single vendor or free-tier cap can stall the pipeline.

**Data flow.** `run_analyze.run_baseline()` pulls posts with no analysis row via `db.get_unanalyzed()`, runs `cascade.fast_all()` (VADER compound score + keyword hits) to build a complete row for EVERY post, merges in `pii.masked_fields()`, and upserts with `model='vader-fast'`. Phase 2, `run_llm()`, pulls back only the non-positive rows via `db.get_needs_llm()` (WHERE model='vader-fast' AND sentiment<>'positive'), masks each post's text with `pii.mask()` BEFORE the call, then sends batches of BATCH_SIZE (12) to `llm.analyze_batch()`. That dispatcher walks the chain [LLM_PROVIDER] + LLM_FALLBACKS, routing to `gemini_client`, `ollama_client`, or `openai_compat` (Groq/OpenAI/OpenRouter/DeepSeek/Together/Cerebras/freellmapi) and flipping providers on any exception. Each provider returns `schema.PostAnalysis` pydantic objects — Gemini via native `response_schema`, OpenAI-compat via json_object plus `_coerce()` field-repair, Ollama via its `format` JSON schema. `to_row()` flattens the object (aspects → `aspects_json`, bools → ints) and re-upserts with `model=<provider>`, overwriting the VADER row. Separately, `embed_cluster.main()` reads analysis JOIN raw_posts, embeds text (Gemini `embed_texts` → TF-IDF fallback → identity-matrix last resort), runs cosine AgglomerativeClustering at CLUSTER_DISTANCE=0.35, writes the `clusters` table and stamps `analysis.cluster_id` via `set_cluster()`. Finally `exec_summary.main()` aggregates the whole `analysis` + `clusters` tables, re-masks summaries defensively, and asks the LLM (BRIEF_MODEL) to write `exec_summary.md`, falling back to a deterministic keyless template if no provider answers.

### `analyze/pii.py` · ~87 lines  **[DEMO]**

Fully offline masker, no network, no key. Four compiled regexes (EMAIL_RE, TAXPAN_RE for the Indian income-tax PAN format [A-Z]{5}[0-9]{4}[A-Z], OTP_RE for otp/cvv/pin/code followed by 3-6 digits, DIGITS_RE for 9-22-digit runs) plus a hand-written `_luhn()` checksum. `mask(text)` returns (masked_text, [pii_types]) and disambiguates long digit runs by length + Luhn: 13-19 digits passing Luhn → 'card' (XXXX-XXXX-XXXX-last4), 12 digits → 'aadhaar_or_account', 10 → 'phone' (keep last 2), 9+ → 'account'. `masked_fields(text)` returns the three silver columns {text_masked, pii_types, pii_present}.

**Why it exists.** The compliance layer and the answer to the bank's first question: 'does our customer data leave the building?' ### `analyze/run_analyze.py` · ~107 lines  **[DEMO]**

The orchestrator and CLI entrypoint (`python -m analyze.run_analyze [--phase baseline|llm|both] [--limit N] [--verify]`). `run_baseline()` = get_unanalyzed → cascade.fast_all → merge pii.masked_fields → upsert_analysis. `run_llm()` = get_needs_llm → per-batch PII mask into a `masked` dict keyed by source_id → build llm_batch with text swapped for text_masked → analyze_batch → map results back by source_id → optional `verify_fraud` second pass → `to_row()` → upsert, sleeping SLEEP_BETWEEN_BATCHES between batches. `to_row()` flattens PostAnalysis: pops aspects into `aspects_json`, casts 4 booleans to ints, sets cluster_id=None and model=LLM_PROVIDER (or GEMINI_MODEL). A failed batch is caught and skipped, not fatal.

**Why it exists.** The only place the two-phase cascade, the PII-before-LLM ordering, and the batch-resilience actually happen. Split phases exist so Airflow (experimental/dags/axis_pipeline.py) and mcp_server.py can invoke `--phase baseline` and `--phase llm` as separate tasks — baseline always succeeds keyless, LLM depth is allowed to fail. It's the file to open when a client asks 'walk me through how a post becomes a ticket'.

### `analyze/llm.py` · ~60 lines  **[DEMO]**

60-line provider dispatcher. `_chain()` builds a de-duplicated ordered list of [LLM_PROVIDER] + LLM_FALLBACKS. `analyze_batch(posts)` and `generate_text(prompt, model)` each walk that chain in a try/except, lazily importing gemini_client for 'gemini', ollama_client for 'ollama', and openai_compat (with provider=) for everything else, printing '[llm] provider X unavailable -> next' and re-raising the last exception only if every provider fails. Model overrides (e.g. BRIEF_MODEL) are deliberately applied only to the primary provider. `embed_texts()` is hardcoded to Gemini with no failover.

**Why it exists.** The vendor-lock-in answer. One env var swaps the entire classification engine between Gemini, Groq, OpenAI, OpenRouter, DeepSeek, Together, Cerebras, a local freellmapi aggregator, or fully on-prem Ollama — which is the RBI data-residency story. It also multiplies free-tier quota: hitting one provider's daily cap flips to the next instead of stalling the run. Also imported by warehouse/resolution.py, analytics/actions.py and analytics/translate.py, so it is the shared LLM gateway for the whole repo, not just this subsystem. Covered by 6 tests in tests/test_llm_failover.py.

### `analyze/gemini_client.py` · ~121 lines

google-genai wrapper. Lazy singleton `client()` reading GEMINI_API_KEY. `analyze_batch()` JSON-dumps the batch (text truncated to 4000 chars), builds a GenerateContentConfig with system_instruction=SYSTEM, temperature=0.1, response_mime_type='application/json' and response_schema=list[PostAnalysis] — native schema enforcement — then reads resp.parsed with a raw-JSON re-parse fallback. `_retry_secs()` scrapes the server's `retryDelay: Ns` out of the 429 body (else exponential 2**attempt, capped 65s); `_is_rate()` detects 429/quota/resource_exhausted and breaks after attempt 1 so the dispatcher can fail over fast instead of burning all 5 retries. `verify_fraud(text)` is a second-pass boolean precision check at temperature 0.0 that returns True on any exception. `embed_texts()` chunks 100 at a time against EMBED_MODEL (gemini-embedding-001).

**Why it exists.** The highest-fidelity classification path — the only provider where the pydantic schema is enforced server-side rather than repaired client-side, and the sole source of embeddings for clustering. Without it `embed_cluster` silently degrades to TF-IDF and `--verify` becomes a no-op.

### `analyze/openai_compat.py` · ~200 lines

The widest provider path — one client for any /v1/chat/completions endpoint. `_client_model()` resolves (base_url, key_env, default_model) from config.OPENAI_COMPAT and builds an OpenAI client with max_retries=0, timeout=20 so the SDK doesn't stack its own backoff on top. Because json_object mode does NOT enforce pydantic, this file carries the repair kit: `_items()` unwraps results/posts/analysis/items/data envelopes, `_loads()` strips ```json fences and salvages the first {...}/[...] block out of prose, `_enum()`/`_num()` clamp bad enum values and out-of-range floats, and `_coerce()` merges a 20-key `_DEFAULTS` dict over the model output to build a valid PostAnalysis. SCHEMA_HINT is auto-generated from PostAnalysis.model_fields and appended to SYSTEM. `_is_rate()`/`_is_conn()`/`_retry_after()` drive fast failover. Notably it refuses positional source_id backfill unless len(items)==len(posts) — an explicit guard against mis-stamping an analysis onto the wrong post.

**Why it exists.** This is what makes the 'pluggable provider' claim real for the 7 non-Gemini vendors, and it's why a partially-malformed LLM response degrades into a usable row instead of dropping the post. The alignment guard is the bank-safety detail: a mis-attributed fraud flag on the wrong customer would be worse than no flag. ### `analyze/cascade.py` · ~69 lines

The free tier. Module-level VADER SentimentIntensityAnalyzer plus two hardcoded keyword lists: RISK_KW (25 terms — fraud, otp, refund, debited, stuck, not working, blocked, kyc, crash…) and FRAUD_KW (9 terms). `classify_fast()` returns compound score + matched hits + a label at the standard ±0.05 thresholds. `fast_row()` builds a COMPLETE 24-key analysis row from VADER alone — deriving emotion, intent, urgency (high if negative AND risky) and fraud_signal (any FRAUD_KW substring) — and sets summary to the PII-masked first 90 chars of the post, model='vader-fast'. `needs_llm(row)` is simply `row['sentiment'] != 'positive'`. `fast_all()` maps over posts. `split()` at the bottom is labelled 'kept for backwards-compat'.

**Why it exists.** The unit-economics story: every post gets a real sentiment for free and instantly, so the table is never skewed positive by unscored rows, and the paid LLM is spent only on the ~45% of posts a bank must act on. It's also the graceful-degradation floor — with zero API keys the pipeline still produces a populated dashboard. `classify_fast` is additionally reused by analytics/competitor.py for competitor benchmarking.

### `analyze/embed_cluster.py` · ~109 lines

Standalone CLI (`python -m analyze.embed_cluster`). `_embed()` tries analyze.llm.embed_texts, falls back to a keyless sklearn TfidfVectorizer(max_features=512) — patching all-zero rows to 1e-6 so cosine linkage doesn't crash on stopword-only posts — and falls back again to np.eye() if even that fails. `main()` reads analysis JOIN raw_posts, runs sklearn AgglomerativeClustering(n_clusters=None, distance_threshold=CLUSTER_DISTANCE=0.35, metric='cosine', linkage='average'), then per group computes size, avg_score, `_mode()` of theme as the title, `_mode()` of recommended_team as top_team, 5 sample_ids, and recent_share = fraction of posts within 24h of the LATEST post timestamp (not wall-clock, so 'emerging' works on static seed data). Writes the `clusters` table via upsert_cluster and stamps analysis.cluster_id via set_cluster per post. Prints TOP ISSUES and an EMERGING NEGATIVE ISSUES alarm (recent_share>=0.6 AND size>=2 AND avg_score<0).

**Why it exists.** The volume-to-issue collapse that makes the deck's '500 people saying the same thing = one issue, count 500' claim, and the source of the dashboard's Root Cause panel and the emerging-spike alarm. Without it there are no clusters, the cluster panel is empty, and exec_summary's 'top issues' section has nothing to rank.

### `analyze/exec_summary.py` · ~108 lines

## transform/ + warehouse/ — clean stage & star schema

**Purpose.** This is the middle and back half of the pipeline: `transform/beam_transform.py` is an Apache Beam job that turns raw scraped posts into normalised, deduped, language-tagged, PII-masked `clean_posts`; the `warehouse/` package then turns `raw_posts + analysis` into a real Kimball star schema (SCD Type 2 author dimension, conformed date/source/team/category dimensions, three fact tables) plus the business marts the Streamlit war-room and FastAPI actually read — RM cockpit, admin analytics, and the headline KPI row including Sentiment Recovery Rate. It exists so the demo can answer "this isn't a sentiment script, it's a warehouse" — with a data-quality gate that can roll a bad build back before it reaches the dashboard.

**Data flow.** `run_harvest.py` runs fetch → `transform.beam_transform.run()` (raw_posts → clean_posts) → VADER baseline → LLM depth (writes `analysis`) → `warehouse.build.ensure_tables()` + `db.snapshot_tables()` (snapshots 21 derived tables as last-good) → clustering → `warehouse.build.main("all")`. Inside that: `build_dim_author()` writes SCD2 versions per handle; `build_facts()` joins `raw_posts ⨝ analysis`, drops Axis's own handles, maps `author_key` from dim_author and `customer_key` from `bridge_handle_customer`, derives `created_date`/`date_key`/`source_key`, and atomically replaces `fact_mention` + explodes `aspects_json` into `fact_aspect_sentiment`; `resolution.build_interactions()` reconstructs threads by `conversation_id` into `fact_interaction`; `build_marts()` produces `mart_rm_enablement` (via `xsell.recommend()`), `mart_admin_analytics`, `mart_kpis`; then `star.build_all()` adds `dim_date`/`dim_source`/`dim_team`/`dim_category`, the `fact_daily` aggregate, `mart_channel`, and the `vw_mention`/`vw_daily_sentiment` views. Finally `dq_checks.run()` returns 14 assertions — on any FAIL `run_harvest` calls `db.restore_tables()` and the bad build never publishes. Note the transform output (`clean_posts`) is a side branch: the warehouse reads `raw_posts`, not `clean_posts`.


### `transform/beam_transform.py` · ~169 lines  **[DEMO]**

Apache Beam pipeline raw_posts -> clean_posts, fully keyless. `_clean()` strips URLs, the `RT` prefix and zero-width chars, collapses whitespace, and md5s a normalised (lowercase, a-z0-9 + Devanagari only) form into `text_hash`. `_mark_dups()` runs after GroupByKey on that hash, sorts the group by real parsed timestamp (`_ts_key`, unparseable dates sort last) and marks the earliest canonical — it is stateful across incremental runs via a `seen_hashes` set of canonical hashes already in clean_posts. `_detect_lang()` returns hi (Devanagari regex), hi-en (>=2 hits against an 18-word HINGLISH token set) or en. `_is_spam()` fires on >=3 URLs, any of 12 PROMO substrings, >=6 emoji, or 7+ repeated chars. `_enrich()` calls `analyze.pii.mask()` and emits the `db.CLEAN_COLS` row. `WriteCleanPosts(beam.DoFn)` buffers per bundle in start_bundle/process/finish_bundle and sinks via `db.upsert_rows('clean_posts', …)`. `run()` wires Create -> Clean -> KeyByHash -> GroupByKey -> MarkDup -> Enrich -> ParDo(Write) then prints dup/spam/pii/lang stats. CLI flags `--runner --limit --all`; runner defaults to `config.BEAM_RUNNER` (DirectRunner).

**Why it exists.** It is the only distributed-processing engine in the stack and the reason the deck can say "Apache Beam / Dataflow-ready". It produces `clean_posts` (1,769 rows live), which feeds `analytics/translate.py` (the Hindi/Hinglish translation queue), the dashboard language-mix panel in `dashboard/panels.py`, and the dq_checks "transform ran" assertion. Without it there is no dedup, spam, or language layer at all and the Airflow DAG's `transform` task fails.

The gold-layer builder. ### `warehouse/__init__.py` · ~1 lines

A single docstring line: "Gold layer — Kimball star schema + marts on top of raw_posts/analysis (silver)." No code.

**Why it exists.** Makes `warehouse` an importable package. build/star/resolution/dq_checks/xsell all import each other as `warehouse.x`, and run_harvest.py, the Airflow DAG, mcp_server.py and the tests all invoke `python -m warehouse.build` / `python -m warehouse.dq_checks`. Delete it and every one of those entry points breaks.

**Know before a client digs in:**

- THE BIG ONE — the Beam dedup and spam flags are computed and then ignored. `build_facts()` reads `raw_posts JOIN analysis`; it never joins clean_posts. Verified live: 144 rows flagged `is_duplicate=1` and 18 flagged `spam_flag=1` are sitting inside fact_mention and are counted in every mart and every KPI. If a client asks "so you deduplicate?", the honest answer is "we detect duplicates, we don't yet exclude them from the facts."
- The Beam PII mask is duplicated work that nothing consumes. `_enrich()` masks into `clean_posts.clean_text`, but the LLM path in analyze/run_analyze.py re-masks `raw_posts.text` into `analysis.text_masked` and sends that to the model. The only reader of `clean_posts.clean_text` in the whole repo is `analytics/translate.py`.
- "Swap BEAM_RUNNER=DataflowRunner for cloud scale" (docstring line 12) is untested and would fail as written. `PipelineOptions(flags=[], runner=runner)` passes no --project/--region/--temp_location/--setup_file, and `WriteCleanPosts` writes through a module-global SQLAlchemy engine that Dataflow workers would neither have configured nor be able to reach. The `seen_hashes` set is also serialised into the FlatMap as a plain Python object rather than a Beam side input, which does not scale. Do not offer a live Dataflow run.
- dim_author has SCD2 version explosion: 7,866 rows for 1,216 distinct handles, max version 12 (805 handles have a v2, 3 have a v12). `complaint_count` is one of the six tracked attributes and it is a cumulative counter, so any author who posts again mints a new version on EVERY rebuild. The `_sigval()` NaN/None fix stopped a worse variant but not this design flaw. A Kimball-literate reviewer spots this in seconds — have the answer ready: counts belong in the fact, not in a Type-2 dimension; in prod the dbt snapshot would track a reduced attribute set.
- The headline "Sentiment Recovery Rate = 25%" is literally 1 out of 4. Live fact_interaction: 588 threads, only 4 have any bank reply, resolved=4, customer_satisfied=1, and 584 threads have resolution_type='none'. The denominator in build.py is "threads that got a response" — n=4. This is the single most quotable number in the demo and it has no statistical basis.
- 62% of the admin mart is unclassified. The largest row in mart_admin_analytics is `(not_applicable, none)` with 1,083 of 1,754 mentions. Overall 1,697/1,754 facts have rbi_category NULL or 'not_applicable' and 1,086 have no recommended_team — because 963 of 1,769 analysis rows are still `model='vader-fast'` with no LLM pass. The dim_category "RBI compliance slicing" story is thin against the actual data.
- mart_rm_enablement emits a broken sentence for happy customers. When a customer has no negative mentions, build.py sets `pain_area="none"` and `pain="No negative mentions on record"`, and the talking_point f-string produces: "Lead with the none issue (No negative mentions on record); once acknowledged, pitch Axis Max Life Term / Health Cover." That exact string is live on 3 of the 6 customers in the RM Cockpit tab. Fix the f-string tonight or do not scroll that column.
- dim_product is an orphan dimension. Created in build.py's DDL, seeded with 9 rows by sample_data/seed_crm.py, and never joined by any fact, mart or view. xsell.py hardcodes product names instead of reading it, and fact_mention has a free-text `product` column with no FK to product_code.
- fact_aspect_sentiment is built but never read. 801 live rows exploded from `analysis.aspects_json`; no dashboard panel, API endpoint, mart or view queries it. It appears only in `db.GATED_TABLES` for snapshot/restore.
- vw_mention — the ~35-column "one-stop analytical view" — has no production consumer. It is referenced only by tests (test_star.py, test_gate.py, conftest cleanup). The dashboard reads vw_daily_sentiment and mart_channel but never vw_mention. Same for dim_team and dim_category, which exist purely to be joined inside that unused view. Frame all three as "the BI-ready layer your Power BI team connects to", not as something the demo exercises.
- dq_checks is not a gate on its own, and the docs contradict the code. Its own docstring and docs/adr/ADR-001 admit the build writes marts to the live DB BEFORE it runs; only run_harvest.py's snapshot/restore makes it behave like a gate. Running `python -m warehouse.dq_checks` standalone just turns a run red. Separately, RUNBOOK.md and CLOUD-MIGRATION.md both say "expect 11/11" while `run()` actually returns 14 checks — stale docs a client could catch.
- The dedup key is aggressive on short text. `_clean()` md5s the text after lowercasing and stripping everything except a-z0-9/Devanagari/space, so two genuinely different customers each posting "UPI not working" collapse into one canonical plus one duplicate. Fine for demo volume, wrong at scale.
- Every threshold is a hardcoded magic number with no config knob and no derivation from labelled data: influence tiers 100/1000/10000 (`build._tier`), sentiment label ±0.15 and trend ±0.1 (build_marts), satisfaction at score>0.2 (resolution), spam at >=3 URLs / >=6 emoji / 7+ repeated chars (beam), the 18-word HINGLISH list, and all of star.py's SOURCE/TEAM/CATEGORY seeds including per-team SLA hours of 2–72. If asked "how did you pick 0.15?" the true answer is "judgement, not tuning."
- `_llm_refine()` in resolution.py can only make the numbers look better — it flips resolved 0->1 and customer_satisfied None->1 and never the reverse, an obvious optimism bias. Its docstring says "one cheap LLM call" but it loops one call per unresolved responded thread. It is off by default (RESOLUTION_LLM=0), so the demo numbers are 100% heuristic; say so rather than implying an LLM validated them.
- Minor dead/awkward code a curious reader will hit: `ts = db.now()` at star.py line 119 is assigned and never used; `star.backfill_fact_keys()` is redundant because `build_facts()` already sets date_key/source_key before the atomic write (build.py even comments on this); and resolution.py imports the private `_norm` plus FACT_INTERACTION_COLS from warehouse.build while build.main() imports resolution back — a circular coupling that only works because the imports are function-local.
- dim_date spans 4,667 days (2013-09-27 to 2026-07-07) because it is generated from MIN/MAX of fact created_date and at least one scraped post carries a 2013 timestamp. A 13-year calendar in a social-listening warehouse looks odd on screen — expect "why do you have 2013 data?"
- star.SOURCE_SEED hardcodes 12 channels while the pitch says 9 public sources (twitter and youtube are seeded with is_keyless=0). Meanwhile fetch/ contains ~20 fetcher modules — instagram, linkedin, tiktok, trustpilot, mouthshut, googlereviews, facebook, consumercomplaints, scrapebadger — whose source keys are NOT in SOURCE_SEED. Live data currently has zero orphan source_keys, but `build_mart_channel()` uses an INNER JOIN to dim_source, so enabling any of those fetchers would silently drop those mentions out of mart_channel and out of every dim_source-joined view, with no error.
- THE REAL BIG ONE — the Airflow DAG never runs the star step, so its own dq_check task fails deterministically. experimental/dags/axis_pipeline.py lines 100-103 create only wh_dims/wh_facts/wh_resolution/wh_marts (`warehouse.build --step dims|facts|resolution|marts`); `--step star` is a valid choice in build.py's argparse but is never invoked. build_static_dims/build_dim_date/build_fact_daily/build_mart_channel/create_views therefore never run under Airflow. Because build_facts() now sets date_key inline, the two star-layer assertions break. I ran the DAG's exact four steps against a fresh temp DB and got 12 PASS / 2 FAIL: 'dim_date covers all fact date_keys — 1 uncovered' and 'fact_daily reconciles to keyed facts — fact_daily=0 vs date_key=1'. The `dq_check` BashOperator sys.exit(1)s, the DAG goes red, and the entire downstream `features` TaskGroup (line 116: dq_check >> features) never runs. The doc calls dq_checks 'the most credible file in the repo' and build.py 'the one the Airflow DAG calls four separate times' without noticing the fifth step is missing and that this makes the advertised orchestration path fail on every run.
- The rationale comment in dq_checks.py lines 77-78 is stale and no longer true: 'reconcile fact_daily against date_key (BOTH derive from the star step) so the check is self-consistent whether or not star.build_all() ran: 0==0 before it, N==N after.' date_key no longer derives from the star step — build_facts() sets it at build.py:216 (with its own comment bragging about the change). The invariant the comment protects was silently broken by that fix, which is the direct cause of the Airflow failure above. A reviewer who reads the comment and then the code catches a contradiction inside a single file.
- resolution.py orders threads by raw string, not parsed datetime — the one place the repo's own 'mixed-date-format fix' was NOT applied. build_interactions() line 64 does `g.sort_values("created_at")` and line 81 does `cust[cust["created_at"] > first_resp]`, both lexicographic on the raw TEXT column. raw_posts.created_at holds at least 6 shapes (ISO+offset 911 rows, naive ISO 474, ISO-offset 57, ISO .mmmZ 52, +HHMM 34, and RFC-822 'Mon, 29 Jul 2026 ... GMT' ~120). RFC-822 always sorts after every ISO string regardless of real time, and offset-bearing timestamps mis-order against Z. I diffed string-order vs pd.to_datetime(format='mixed') order per thread: 3 of 598 threads are currently mis-ordered, and 8 threads contain more than one format. That misidentifies the inbound post, the first bank reply, and the 'post-response' customer post — i.e. it corrupts exactly the n=4 denominator behind the headline Recovery Rate. Note the contrast the doc misses: beam_transform._ts_key deliberately uses db.parse_dt for the same problem, and resolution.py itself uses format='mixed' inside _hours_between — so the latency is computed correctly on rows that may have been picked wrongly.
- SLA_RESPONSE_HOURS is dead config that the warehouse README advertises. config.py:212 defines it, warehouse/README.md:47 lists it as one of the four warehouse config knobs, and grep finds zero code references anywhere in the repo. Nothing computes an SLA breach: MART_ADMIN_COLS has avg_response_latency_min and no SLA measure, while dim_team.sla_hours (2-72h, seeded in star.py) surfaces only inside vw_mention — the view the doc itself establishes has no production consumer. So README's grain-table entry 'mart_admin_analytics | category x team | follow-up bifurcation + SLA' is unbacked. This is a live client-facing claim, unlike the dbt paragraph the doc praises.
- The Beam PII mask ignores config.PII_MASK. _enrich() (beam_transform.py:98) calls pii.mask() unconditionally, while analyze/run_analyze.py:44,62 gates masking behind `if PII_MASK`. warehouse/README.md:48 lists PII_MASK=1 as a governance knob. Setting PII_MASK=0 therefore silently produces an inconsistent state — analysis.text_masked unmasked, clean_posts.clean_text still masked — which undercuts the 'where PII lives' layer diagram the doc calls the file's best asset.
- build_marts() runs the status() closure over every fact row twice, the second time via iterrows(). build.py:326 already materialises `fm['followup'] = fm.apply(status, axis=1)`, then line 347 recomputes it row-by-row: `needs_fu = int(sum(1 for _, r in fm.iterrows() if status(r) != 'no_followup'))`. It could read the column that was just built. At 1,754 rows it is invisible; it is the kind of thing a data architect reading build_marts top-to-bottom will point at, and it sits ten lines from the KPI row the demo leads with.
- fact_mention.date_key and source_key are not in build.py's DDL — they exist only because star.ensure() ALTERs them in (star.py:112-113), yet build.py's FACT_MENTION_COLS (line 33) lists them and build_facts() writes them. build_facts() is therefore only safe because main() always calls ensure_tables() first. Running `python -m warehouse.build --step facts` against a DB whose fact_mention predates star.py works only by that side effect. Worth knowing before anyone hand-runs a single step during a demo.

## analytics/ — insight marts

**Purpose.** The insight/mart layer that sits between the star-schema warehouse and the Streamlit war-room + FastAPI. It turns the classified post table (`analysis` joined to `raw_posts`) into 13 business-facing marts — product scorecards, influencers, team queues, fraud board, RBI-category trends, geo, competitor share-of-voice, churn risk, forecast, entities — plus the "so what" layer: LLM-drafted public replies, real-time alerts, Hindi/Hinglish translation, an audit log with PII-masked export, the weekly exec digest, and model-drift/cost tracking. Everything here is keyless-by-default (pure pandas aggregation) with LLM used only where it adds language, so the demo runs even with no API key.

**Data flow.** `analytics/features.py::_base()` is the single entry point for the whole subsystem: it runs one SQL join of `analysis` to `raw_posts`, drops posts authored by Axis's own handles (via `config.AXIS_HANDLES` + `warehouse.build._norm`), and hands a DataFrame to every builder. `ensure_tables()` creates the 17 analytics tables (its `DDL` list) on top of the warehouse's dims/facts. Each builder does DELETE-then-write into a `mart_*` table; `build_all()` runs the six aggregation marts plus competitor SOV. `intelligence.py` re-uses the same `_base()` for churn/forecast/entities, `actions.py` reads `analysis` + `clusters` + `mart_kpis` to emit `reply_drafts`, `alerts`, `audit_log` and `weekly_digest.md`, `translate.py` reads `clean_posts` where lang is hi/hi-en, `competitor.py` fetches Google News RSS per rival into `competitor_posts` then calls `build_competitor_sov()`. `run_harvest.py` orchestrates the order (steps 8-13); Streamlit `dashboard/panels.py` and `api/main.py` only ever SELECT from the finished marts, never recompute. All 21 mart tables are listed in `db.GATED_TABLES`, so a DQ-gate failure restores the previous good copy.


### `analytics/features.py` · ~299 lines  **[DEMO]**

The mart engine. Holds the `DDL` list that CREATEs all 17 analytics tables (mart_product_scorecard, mart_influencers, mart_team_queue, mart_fraud, mart_trends, mart_geo, competitor_posts, mart_competitor_sov, reply_drafts, alerts, audit_log, mart_churn_risk, mart_forecast, mart_entities, translations, eval_history, run_metrics) plus their column lists. Key functions: `ensure_tables()` (calls warehouse.build.ensure_tables then executescript(DDL)); `_base()` — the shared SQL join of analysis+raw_posts that excludes Axis's own handles; `build_product_scorecard()` (mentions/pct_negative/complaints/nps_proxy per product); `build_influencers(top=25)` (reach = max(engagement, view_count), stance thresholds at +/-0.15, worst_summary); `build_team_queue()` (open_items/critical/fraud per recommended_team, using the NEEDS_FOLLOWUP intent set); `build_fraud_board()`; `_zscores()` + `build_trends()` (per-RBI-category daily volume, anomaly=1 when z>=2 AND avg_score<0); `infer_city()` + `build_geo()` over the 31-key CITY_REGION dict; `build_competitor_sov()`; `build_all()`.

**Why it exists.** Every mart-backed tab in the Streamlit war-room and most FastAPI endpoints read tables this file creates and populates. Delete it and `ensure_tables` disappears — intelligence.py, translate.py, ops.py and actions.py all import from it, so the entire tier-2/3/4 layer fails to import and the dashboard falls back to 'Run python -m analytics.features' placeholders on 7+ tabs. It is also the only place `_base()` (the customer-voice-only definition) lives, so it is the file to open when a client asks 'how do you know this is a customer complaint and not the bank's own tweet?'

### `analytics/actions.py` · ~169 lines  **[DEMO]**

The action + governance layer. `audit(actor, action, detail)` writes md5-keyed rows to audit_log. `export_masked(sql, actor)` runs a query and swaps `text`/`clean_text` for `text_masked` before returning, then logs the export. `draft_replies(limit=15)` selects negative/mixed posts with intent in (complaint, churn_threat, legal_threat, fraud_report) that have no draft yet, ordered by urgency then score, and sends the **PII-masked** text to `analyze.llm.generate_text` with `_PROMPT` ('max 280 chars, Do NOT admit liability, invite them to DM'), falling back to the hardcoded `_TEMPLATE` string if no LLM. `build_alerts()` emits three alert kinds — emerging negative clusters (recent_share>=0.6, avg_score<0, size>=2), fraud spike (fraud_signal count >= 5), and unresolved-critical SLA — then `_dispatch()` POSTs them to `$ALERT_WEBHOOK` if set. `weekly_digest()` writes weekly_digest.md from mart_kpis + mart_competitor_sov + clusters. CLI: `python -m analytics.actions [respond|alerts|digest|all]`.

**Why it exists.** This is the file that converts 'we detected sentiment' into 'we did something about it' — the whole reason a bank buys the tool. It also carries the two compliance talking points a banking client will probe: PII is masked before any text reaches a third-party LLM (`text_masked` in the draft query), and every export is written to an audit trail. Without it there are no reply drafts, no alerts panel, no digest, and no audit tab.

### `analytics/intelligence.py` · ~160 lines

Tier-2 'predictive' marts, all keyless. `churn_features(d)` aggregates per author (mentions, complaints, churn_threat count, avg_score, neg_ratio, churn_flag). `build_churn(top=50)` fits a sklearn `LogisticRegression(max_iter=500, class_weight='balanced')` on those features with label y = (churn_flag==1 | churn_threat>0), predicts on the same rows, falls back to a weighted heuristic (0.5*neg_ratio + 0.3*has_complaint + 0.2*has_threat) when there is no trainable signal, joins `bridge_handle_customer`/`dim_customer` to attach real customer names, and writes mart_churn_risk with a `top_factor` explanation string. `forecast_series(vals, horizon=3)` is a numpy `polyfit` degree-1 linear extrapolation with a rising/falling/flat label at slope +/-0.3; `build_forecast()` applies it per RBI category into mart_forecast. `extract_entities()` + `build_entities()` are keyword matching against a 16-item `AXIS_PRODUCTS` list and the imported CITY_REGION dict, written to mart_entities.

**Why it exists.** Feeds the Churn Risk, Forecast and Entities tabs (dashboard/panels.py churn_panel/forecast_panel/entities_panel and the /churn, /forecast, /entities API endpoints). It exists to answer 'can it predict, not just report?' — but the implementation is heuristic-grade, so it should be described as a scoring layer, not a model. See gotchas before opening it in front of a data scientist.

### `analytics/competitor.py` · ~53 lines

53 lines, keyless. `fetch_brand(brand, limit=15)` builds a Google News RSS URL (`news.google.com/rss/search?q="HDFC Bank"&hl=en-IN&gl=IN`), parses it with feedparser, scores each title+summary with `analyze.cascade.classify_fast` (VADER), and dedupes into `competitor_posts` rows keyed by md5(brand+link). `run(limit=15)` loops `config.COMPETITORS` = ['HDFC Bank','ICICI Bank','SBI','Kotak Mahindra'], upserts, then calls `analytics.features.build_competitor_sov()` to rebuild mart_competitor_sov. Currently 288 competitor_posts in axis.db.

**Why it exists.** Supplies the Share-of-Voice tab (the first panel in dashboard/panels.py and the /competitor-sov API endpoint) — the 'how do we compare to HDFC/ICICI/SBI/Kotak' slide. Without it mart_competitor_sov has only the Axis row and the SOV panel and the weekly digest's SOV section go blank. The methodology is its weak point, not the code (see gotchas).

### `analytics/ops.py` · ~77 lines

Tier-4 model governance. `record_quality()` appends three drift proxies to eval_history each run: llm_coverage_pct (share of rows whose model != 'vader-fast'), avg_confidence, and high_conf_pct (confidence >= 0.5). `drift_flags()` compares the latest eval_history snapshot to the previous one and flags any metric that dropped more than 15%. `estimate_cost()` groups `analysis` by model, multiplies by the module-level `PRICE` table (per-million-token USD) and the constants `TOK_IN, TOK_OUT = 300, 200`, and upserts a run_metrics row (mentions, llm_calls, tokens_est, cost_usd_est, provider). `run_all()` runs both. Real data present: 3 run_metrics rows and 9 eval_history rows showing LLM coverage moving 27.5% -> 47.0% -> 45.6%.

**Why it exists.** It is the answer to the two questions a bank's model-risk and procurement people always ask: 'how do you know the model hasn't drifted?' and 'what does this cost per run?'. Powers the Quality and Cost panels (panels.py quality_panel/cost_panel, which imports `drift_flags` directly) and the /cost API endpoint. Show the panel rather than the source — the pricing constants are illustrative.

### `analytics/translate.py` · ~47 lines

47 lines. `translate(limit=25)` selects clean_posts where lang in ('hi','hi-en') that have no row in `translations` yet, sends each through `analyze.llm.generate_text` with a fixed 'output ONLY the English translation' prompt (using config.BRIEF_MODEL), and stores source_id/lang/english/model. If `analyze.llm` fails to import or the call raises, it stores the original text with model='passthrough' so the pipeline never blocks. run_harvest calls it with limit=200.

**Why it exists.** The India-specific differentiator — 79 of 1769 posts are Hindi or Hinglish and would otherwise be scored by VADER on text it cannot read. It backs the Language panel (panels.py language_panel LEFT JOINs translations onto clean_posts). Actual state is good: all 79 were translated by a real LLM (42 hi + 12 hi-en via freellmapi, 17 + 8 via groq), zero passthrough fallbacks.

### `analytics/__init__.py` · ~4 lines

A three-line module docstring only — no imports, no exports, no `__all__`. It just names the layer ('marts + active modules for the Axis product features... Keyless where possible; LLM optional').

**Why it exists.** Only exists to make `analytics` an importable package so `python -m analytics.features` and `from analytics import features, intelligence` work in run_harvest.py, the Airflow DAG, and the tests. Nothing to explain if a client clicks it.

**Know before a client digs in:**

- STALE MARTS — FIX BEFORE THE DEMO. mart_trends and mart_forecast in axis.db were built 2026-07-07 20:05, one day BEFORE commit de0f459 fixed the mixed-date parse bug ('NULLed 87% of dates'). mart_trends currently has 19 rows covering 474 of 1754 mentions and ZERO anomalies flagged. The LogisticRegression is fit and scored on the SAME rows (no train/test split), and the label y = (churn_risk flag OR churn_threat intent) is itself encoded in the features (neg_ratio, complaints) — textbook leakage, so the probabilities saturate. Worse, the #2 entry is @MyIndusIndBank — IndusInd Bank's official corporate handle — at churn_prob 1.0 with 50 mentions, 0 complaints and top_factor 'monitor'. All 50 entries are kind='handle' (bridge_handle_customer has only 6 seeded rows and none matched), so no named customer ever appears. If asked, call it a rules-weighted risk score, not a validated model.

Thresholds are hardcoded lifetime counts with no time window (fraud >= 5 ever, critical >= 1 ever), so both 'critical' alerts are permanently on and are not 'real-time' in any meaningful sense. All rows have sent=0 — ALERT_WEBHOOK is unset, so no alert was ever dispatched anywhere. The emerging-negative-cluster branch (the impressive one) has produced zero rows to date.
- audit_log IS EMPTY (0 rows). `audit()` is only reached through `export_masked()`, which is only called from the dashboard's export button (panels.py:390). The compliance/audit tab will render blank. Click Export once before the client walks in so there is at least one row to point at.

- REPLY DRAFTS ARE NOT SAFE TO READ ALOUD. 6 of 65 are the hardcoded fallback template. The LLM ones contain literal unfilled placeholders ('Dear [Customer]', 'Dear @username'), are wrapped in the model's own quotation marks, and at least one tells the customer to 'DM us with your account details' — a data-collection red flag any bank compliance officer will catch. The prompt guards against admitting liability but says nothing about requesting account data.
- mart_product_scorecard has 133 rows, 81 of them with a single mention, because `analysis.product` is unnormalized free-text LLM output: 'credit card' (24) and 'credit_card' (19) are separate rows, as are 'banking' / 'banking services' / 'general' / 'other' / 'none' — the code only filters the literal string 'unspecified'. A client scrolling that table sees an obviously ungoverned dimension.
- mart_fraud has the same cardinality problem and it is worse optically: the single largest bucket is 'suspected' (47 of 125) which is just the NULL fallback, plus case-duplicates ('ACCOUNT_FRAUD' vs 'account fraud', 'PHISHING' vs 'phishing') and 27 single-mention types.

- COST TRACKING IS A HARDCODED GUESS, and it is visible on lines 10-15 of ops.py. TOK_IN/TOK_OUT are fixed at 300/200 tokens per post (never measured), and `PRICE.get(model, (0.0, 0.0))` silently prices anything unlisted at zero — including 'freellmapi', which is 456 of the classified rows, and 'groq' (258), both explicitly set to $0.00. The visible symptom: cost_usd_est is identical at $0.0408 across three runs whose LLM call counts were 350, 772 and 806.
- Geo and 'NER' are substring keyword matching, not models. `infer_city()` returns the FIRST key that appears anywhere in the raw text (dict insertion order), so a post naming two cities is credited to whichever iterates first, and URLs are matched too. Only ~81 of 1754 posts matched at all — 12 cities, three with <=2 mentions. In intelligence.py the 16-item AXIS_PRODUCTS list matches the ordinary English word 'asap', which is why mart_entities lists 'Asap' as an Axis product with 5 mentions; 'Atlas' and 'Privilege' are similarly ambiguous.
- weekly_digest() is not weekly — there is no date filter anywhere in it, so it summarizes the entire table for all time. It also writes to the relative path 'weekly_digest.md', i.e. the process CWD, so under Streamlit Cloud or Docker it lands wherever the container started, not next to the repo.
- Non-atomic mart refreshes. Every builder does `db.execute('DELETE FROM mart_x')` followed by a SEPARATE `db.upsert_rows`/`insert_rows` call — two transactions. db.py already exposes `replace_rows()` (atomic DELETE+INSERT in one transaction, with a docstring explaining exactly this hazard) and warehouse/build.py was migrated to it; analytics never was. A live dashboard or API reader hitting Neon mid-rebuild can see a mart as empty. Partially masked by the DQ-gate snapshot in run_harvest, but the window is real.
- Fraud numbers do not reconcile across panels. build_alerts counts fraud from raw `analysis` (126) while mart_fraud counts from `_base()` (125). Worse, dashboard team_queues() filters `WHERE team <> 'none'` and the 'none' bucket holds 52 of the 125 fraud-flagged posts — so the team queue visibly accounts for only 73 fraud items while the fraud board shows 125.
- competitor.py has no relevance filter and no cross-brand dedupe — a Google News RSS hit for 'SBI' is accepted on string match alone, and `created_at` is the raw RFC-822 published string, a different format from every social source.
- Minor dead weight: features.py imports `json` solely for one print statement in build_all(); analytics/__init__.py is a docstring with no exports; and the 'keyless pure aggregation' layer still hard-imports `warehouse.build` for `_gold_tables` and `_norm`, so analytics cannot run without the warehouse module.
- _dispatch() (actions.py:126) runs `UPDATE alerts SET sent=1 WHERE sent=0` — it marks EVERY unsent alert in the table as sent, not just the rows it POSTed. One successful webhook call silently retires the entire historical backlog, so sent=1 cannot be trusted as evidence an alert was ever delivered.
- `pct_negative` does not mean negative. features.py:141, 253 and 268 all compute it as `sentiment.isin(['negative','mixed'])`, and nps_proxy subtracts that same combined bucket from positives. The SOV panel's headline "25.7% negative" for Axis, every product scorecard row, and every geo row therefore include mixed-sentiment posts, and no panel label discloses it. A client comparing that number to their own NPS/CSAT will be comparing different definitions.
- draft_replies' SQL (actions.py:48-55) joins raw_posts purely to select r.source_id — a column analysis already has — so the join is dead weight, while clean_posts.clean_text, which IS PII-masked at transform/beam_transform.py:98 and is populated for all 510 rows where analysis.text_masked is NULL, is never consulted. Sourcing the prompt text from clean_posts instead of analysis.text_masked is a one-line fix that eliminates all 11 junk drafts.
- run_metrics is upserted on run_ts = db.now() at second precision (ops.py:63-65), so two runs inside the same second overwrite each other; combined with the full-table recompute this makes run_metrics a snapshot log rather than a per-run ledger, and /cost's `ORDER BY run_ts DESC LIMIT 1` returns the latest cumulative snapshot.
- actions.draft_replies:76 and translate.translate:42 both print the loop-leaked `model` variable after the loop, so the console attributes the whole batch to whichever provider happened to handle the LAST row — e.g. "translated 79 posts (groq)" when 54 of the 79 actually went through freellmapi. The same pattern makes the harvest log's provider attribution unreliable.
- The translations table has the same cosmetic defect the doc flags for reply drafts but leaves unflagged for the Language panel: 75 of 79 stored English translations are wrapped in the model's own quotation marks. Also, the reply prompt (_PROMPT) never pins the output language, which is why one stored draft is in Hindi/Devanagari.
- build_influencers' reach is the MAX of (engagement, view_count) across that author's posts, not a sum — an author with 40 posts ranks on their single best-performing one. The top-25 cut is by reach alone with no stance or volume filter, so the "Influencer watch" list is a reach leaderboard, not a risk list; stance is a display column only.
- build_forecast fits a single degree-1 polyfit across a category's ENTIRE daily history (201 days for not_applicable) with no seasonality, no recency weighting and no gap handling. Because the underlying series is a scrape-volume series, the rising/falling label mostly encodes when the harvester ran, not customer behaviour — a distinct problem from the staleness the doc flags.
- build_geo and build_entities scan raw_posts.text (raw, unmasked, URLs and @handles included) rather than the PII-masked clean_posts.clean_text every other stage uses. Nothing leaves the process so it is not a compliance breach, but it is the one asymmetry in the "masked everywhere" story and it is also why city keywords match inside URL slugs.
- The export panel's own query (panels.py:391) selects only a.text_masked — it contains neither `text` nor `clean_text`, so export_masked's substitution loop never executes on the one call site that exists in the product. The masking is provided entirely by the caller's column choice, which makes the doc's "PII never leaves via export" docstring purely aspirational; and because text_masked is NULL for 29% of analysis rows, roughly a third of the exported rows will have a blank text column.

## dashboard/ + api/ — what the client sees

**Purpose.** This is the only part of the pipeline a human or an external system ever touches. Everything upstream (9 fetchers -> raw_posts -> clean/transform -> VADER+LLM -> star schema -> 13 marts) writes into axis.db (SQLite locally, Neon Postgres via DATABASE_URL); this subsystem reads it back out two ways — a role-based Streamlit "war-room" for bank staff (exec / RM / ops / analyst), and a read-only REST API so other Axis systems (CRM, ticketing, a BI tool) can consume the same marts without touching the warehouse. It contains no business logic of its own: every number on screen already exists as a row in a mart.

**Data flow.** Both consumers go through one function, db.df(sql, params) in db.py, which is a SQLAlchemy-engine pandas read — so the exact same SQL works against SQLite (demo laptop) or Neon Postgres (cloud) with no code change. Streamlit path: app.py calls fresh(), which runs one wide join (analysis a JOIN raw_posts r ON a.source_id=r.source_id LEFT JOIN clean_posts cp) plus SELECT * FROM clusters, wrapped in @st.cache_data(ttl=1800); two st.fragment blocks re-render off that cache at 1s (KPI strip, clock, scrolling ticker) and 6s (charts, cluster table, priority queue), and apply_filters() slices the cached DataFrame in-memory from sidebar state (source/sentiment/urgency/team/language/free-text/flags/time-window) so filtering never hits the DB. Every other tab is a function in panels.py that issues one _safe() SELECT against its own mart and renders it — mart empty means the panel prints the exact command to build it instead of erroring. theme.py is applied once before anything renders and restyles all ~20 charts by monkeypatching st.plotly_chart. API path is simpler and stateless: request -> per-IP rate-limit middleware -> optional x-api-key dependency -> _rows() -> db.df -> to_dict("records") -> JSON, with all exceptions swallowed into a generic 500 so SQL and table names never reach the client. The only writes from this tier are the audit-log CSV export and the "Run fetch + refresh" button, which shells out to run_window.py as a subprocess and then clears the Streamlit cache.

## eval/ + tests/ — proof it works

**Purpose.** The evidence layer of the POC. A 97-test, fully offline/keyless pytest suite gates every stage of the pipeline (PII masking, VADER cascade, Beam transform, SCD2 dimensions, star schema, DQ gate, 13 marts, FastAPI) against a throwaway database, and a separate harness (eval/run_eval.py) scores the LLM classifier against a hand-labeled gold set to produce the accuracy number quoted to the bank. Without it the whole project is "trust me" — with it, correctness and model quality are demonstrable in 43 seconds on a laptop with no API keys.

**Data flow.** Two independent tracks. (1) Test track: tests/conftest.py runs FIRST at import time — before any project module loads — and rewrites os.environ["DATABASE_URL"] to a temp SQLite file (or to TEST_DATABASE_URL for the Postgres CI leg), plus forces PII_MASK=1 and CASCADE=1, so no test can ever touch the real axis.db. The `fresh_db` fixture then drops 3 views and 38 tables (plus any leftover `*__bak` gate snapshots from db.GATED_TABLES), calls warehouse.build.ensure_tables() and analytics.features.ensure_tables() to recreate the gold+silver schema, and hands `db` back. Each test seeds the bronze layer directly via db.upsert_posts()/db.upsert_analysis()/db.upsert_rows(), then invokes the REAL production build functions (build.build_dim_author, build.build_facts, resolution.build_interactions, build.build_marts, star.build_all, features.build_*, intelligence.build_*, ops.*) and asserts on the resulting fact/mart tables — so the tests exercise the actual pipeline code, not mocks. Pure functions (pii.mask, cascade.fast_row, beam_transform._clean/_detect_lang/_is_spam, features._zscores, run_fetch.cutoff, openai_compat._coerce) are tested directly with no DB. pytest.ini restricts collection to tests/ and disables the cache so CI stays stateless. (2) Eval track: eval/run_eval.py loads eval/gold_set.csv into a list of {source_id, text, source} dicts, calls analyze.gemini_client.analyze_batch() in one shot, joins predictions to gold rows by source_id, and prints sklearn accuracy_score + classification_report for sentiment/urgency/intent plus a line-by-line disagreement list. It writes nothing to the database and returns no exit code.


### `eval/run_eval.py` · ~55 lines  **[DEMO]**

Standalone accuracy harness. Inserts the repo root on sys.path (lines 6-7), reads GOLD = eval/gold_set.csv with pandas, builds posts as [{source_id, text, source:'gold'}], calls analyze.gemini_client.analyze_batch(posts), indexes results by source_id, then for FIELDS = ['sentiment','urgency','intent'] compares p.sentiment.value / p.urgency.value / p.intent.value against the CSV's gold_sentiment / gold_urgency / gold_intent columns. Prints sklearn accuracy_score as a percentage and a full classification_report(zero_division=0) per field, then a '=== DISAGREEMENTS (review these) ===' block listing source_id, field, gold, pred and the first 60 chars of the post. Posts with no returned prediction print 'WARN no prediction' and are skipped.

**Why it exists.** This is the model-governance artifact — the only place in the repo that produces a defensible 'our AI agrees with humans X% of the time' figure. README line 43 calls it 'the credibility number'. Without it the LLM classification layer is unvalidated and a bank's model-risk function has nothing to review. NOTE: it exercises the Gemini client directly, not the failover dispatcher the pipeline actually runs (see gotchas).

## Ops & infra — Docker, CI, tools

**Purpose.** Everything that runs, ships, gates and protects the sentiment pipeline outside the data code itself: two container images (Streamlit dashboard + FastAPI backend), a Postgres docker-compose stack, a 4-job GitHub Actions CI gate (dual-dialect tests + SAST + dependency CVE scan), a scheduled cloud harvest workflow that replaced local Airflow, and four operator scripts (backup/restore, SQLite-to-Postgres migration, .env-to-GitHub-secrets sync, API smoke test). It exists so the POC can be demonstrated as a deployable, testable, auditable system on managed free infrastructure (Neon Postgres + Streamlit Cloud + GitHub Actions) rather than as a laptop script.

**Data flow.** One env var, DATABASE_URL, is the spine — every module, both images, the cron and the tests bind to it. Scheduled path: GitHub Actions `axis-pipeline` fires every 12h, checks out, `pip install -r requirements.txt`, runs `python db.py` (creates schema + indexes on Neon), then `python -m run_harvest`, which executes 14 stages in order — fetch all sources, Beam transform, VADER baseline, LLM depth, snapshot last-good derived tables (ADR-001), embed+cluster, warehouse star build, resolution, feature/intelligence marts, translate, competitor SoV, alerts/digest/replies, exec brief, ops metrics — then runs the DQ gate and either publishes (drops snapshots) or restores last-good and exits 1. The workflow then runs `python -m warehouse.dq_checks` again as a belt-and-braces step. Reads come off the same Neon DB from two places: Streamlit Cloud serving `dashboard/app.py` (built by `Dockerfile` locally) and the FastAPI service from `Dockerfile.api` serving 12 read-only endpoints. Secrets flow one direction: `.env` (source of truth) -> `tools/sync_secrets.py` -> GitHub Actions repo secrets; the Streamlit Cloud DATABASE_URL is set by hand. On every push, `ci.yml` re-runs the whole suite against both SQLite and a Postgres 16 service container via TEST_DATABASE_URL, byte-compiles all packages, and runs bandit + pip-audit.

## experimental/ + docs/ — roadmap & architecture record

**Purpose.** This is the non-live half of the repo. It holds (a) three archived alternative implementations that were built, documented, then deliberately taken out of the production path — a streaming ingest pair, two Airflow DAGs, and a dbt project; (b) the three synthetic seed scripts that bootstrap the demo so the AI layer, the RM cockpit and the north-star metric all have something to show before any real CRM extract exists; and (c) the prose layer a bank's architecture review actually reads — ARCHITECTURE.md, AIRFLOW.md, CLOUD-MIGRATION.md, PITCH.md and two full ADRs. It exists because the project had to prove it could run three different orchestration stories (always-on streaming, Airflow, dbt) while shipping only one, and because the demo has to be reproducible from an empty database.

**Data flow.** The live path is: GitHub Actions cron (every 12h) -> `python -m run_harvest` -> fetch/* into raw_posts -> transform/beam_transform -> analyze cascade (VADER then LLM) -> warehouse/build.py star schema -> 13 marts -> Streamlit + FastAPI read from Supabase. Nothing in experimental/ touches that. experimental/dags/axis_pipeline.py is the same flow re-expressed as 27 Airflow BashOperator tasks (`cd $PROJ && python -m <module>`) grouped ingest/enrich/warehouse/features — the module names and CLI flags it invokes are all real and verified (`fetch.run_fetch --only <src>`, `analyze.run_analyze --phase baseline|llm`, `warehouse.build --step dims|facts|resolution|marts`, `analytics.actions respond|alerts|digest`). experimental/stream/ inverts the same flow into two always-on processes: producer.py (14 poller threads + Bluesky Jetstream + Mastodon SSE + an X cookie-crawler) writes raw_posts continuously; worker.py drains it with the same cascade + PII masking and re-runs `analyze.embed_cluster` every 20 enriched posts. experimental/dbt/ reads the *output* of the Python pipeline — it declares `analysis`, `raw_posts` and `dim_customer` as dbt sources and rebuilds 2 of the 13 marts plus an SCD2 customer snapshot on top. sample_data/ writes directly into raw_posts (seed_posts, seed_thread) and into dim_rm/dim_product/dim_customer/bridge_handle_customer (seed_crm), so the join to CRM and the resolution fact have rows to produce.
